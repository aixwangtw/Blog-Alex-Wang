# 長文與教學文

部落格、教學文、產品介紹這類長文，除了 SKILL.md 的 R1–R56，再照這份做。

## 交稿前自己先砍一輪

第一版永遠太長。下面這些每次都會被砍，先自己砍完再交。

| 砍什麼 | 為什麼 |
|---|---|
| 開場鋪墊（「用起來比想像中平凡」） | 廢話，第一句就該進正題 |
| 過場句（「先講清楚一件常被誤會的事」「回到我們那件事」「有趣的是」「順帶一提」「兩個容易誤會的地方順手澄清」） | 交代自己要講什麼，等於還沒開始講 |
| 英文全名（Application Programming Interface、Graphical User Interface⋯） | 展開沒有解釋任何東西 |
| 端點與變數名（`POST /me/threads`、`creation_id`、DOM、token、server） | 正文一律白話。「先把內容存進平台，再叫它發佈」勝過端點名 |
| 產品沿革（某年某月開源、交給哪個基金會） | 只講現在能怎麼用；沿革兩年後就要回來校對 |
| 對別人專案的評價（「星數太少，稱不上能託付」） | 寫事實就好，判斷留給讀者 |

## 三層分工

表格講原理（通用、不含平台專屬數字），內文講實例（可以有自己的檔名和參數），連結給細節（連到既有的教學）。表格裡出現「某平台每 24 小時 250 則」「某個設定檔名」就是越界了。

## 舉例要讀者裝得到

自己 repo 的檔名（例如 `my_script.js`）只能出現在內文當實例，不能放進「代表性例子」那一欄；那欄放 Claude Code CLI、Playwright MCP 這種查得到、裝得起來的東西。

## 比喻可以留，但要標明只是其中一種情況

「MCP 是 API 和 CLI 的組合包」對初學者好懂，但只涵蓋最常見那種。留著比喻，後面補一句放寬範圍（「但不是每個包都在包既有的東西」），不要換成精準卻難懂的說法。

## 區分兩個東西，講性質不要講數量

「MCP 包得最多：API、CLI、瀏覽器自動化、直接讀檔」是清單，讀者記不住也不會用；「別的殼包完就把裡面藏起來，MCP 包完會列成清單」是性質，一句話就分辨得出來。數量會過期、要維護，性質不會。「星數多少」「支援幾個平台」都該換成「它跟別人差在哪」。

## 分類用動詞，不用名詞

「GUI、API、CLI、MCP 都是介面」是身分宣稱，只要有一個成員層級不同（MCP 是協定不是介面）整句就垮；改成「做的是同一件事：把能力遞出去」是功能宣稱，四個都成立。曾有一篇教學文被連問七題，挑出六個錯，全部是身分宣稱講太滿。

## 補完一段就搜關鍵詞查重複

新增的說明常常跟幾行外的舊段落講同一件事。曾有一次補了「先給目錄、要用才展開」，四行後就有一段一模一樣的說明。補完立刻搜那段的關鍵詞，有第二處就當場合併。

## 例外：全覽型查詢文以「講完」優先

寫「把一個主題能講的都講完」、讓讀者查得到的全覽型文章時，與其他規則衝突的以這裡為準：

- **完整覆蓋勝過砍字。** 「自己先砍一輪」只適用敘事型文章；全覽文的目標是查得到，篇幅長沒關係。開場鋪墊、過場句照砍，內容條目不因篇幅刪。
- **識別字可以進正文和表格。** skill 名、檔名、指令這類讀者要照著找的識別字必須寫出來，不受「端點與變數名一律白話」「表格不放識別字」限制。白話解釋照樣要給，識別字用反引號標。
- **每個宣稱都要查證到原文**（釘死 commit 與行號），查不到的直接不寫。連結不逐句標在正文，文末設「原文依據」一節，按章節分組列；只有直接引述原文句子的地方可以在正文留連結。
- **repo、README、GitHub 這類基本用語不解釋。** 冷僻術語（seam、ADR）加註一次。
- **不逐一列目錄。** 架構是論證式：講為什麼這樣設計、用意是什麼，個別項目只在論證需要時當例子。
- **英文原文可以翻成中文口語轉述**，但翻譯不得添加原文沒有的意思。
- **適合 AI 搜尋引用。** 標題用問句、每節第一句直接回答該節的問題、FAQ 獨立成節。

### 核可文風基準（翻譯外文素材照這個節奏）

> `grill-me` 做的事只有一件：你要動工之前，它先把你的計畫抓來拷問一頓。整件事會被攤成一棵決策樹——每個決定下面，掛著要等它定案才談得下去的其他決定。AI 沿著樹一路問下去，問到沒有任何東西是默默用猜的為止。

要點：短句直述、術語挑口語動詞翻（grill 翻成拷問）、AI 的動作用主動句、原文依據照上面的做法列在文末、不直翻英文句構。
